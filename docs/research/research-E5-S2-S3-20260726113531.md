# GitHub sub-issue 계층 + PR-issue 링크: Research Report
*Generated: 2026-07-26 | Sources: 25 | Adapters: [adapter-exa] | Failed: none (firecrawl 미사용)*

## Executive Summary

GitHub sub-issues는 2025-04 GA됐고 **gh CLI 네이티브 지원은 v2.94.0(2026-06-10)**부터다 — `gh issue edit <parent> --add-sub-issue <n>`. 그 미만 버전은 `gh api` REST/GraphQL fallback이 필요하며, REST의 `sub_issue_id`는 issue number가 아닌 **database id**(잘못 쓰면 HTTP 500/404), GraphQL `addSubIssue`는 node ID를 쓴다. PR-issue 링크의 **유일한 프로그램적 방법은 PR 본문의 closing keyword(`Closes #N`)** — 명시적 링크 생성 API는 REST·GraphQL 둘 다 없다. 그리고 결정적 제약: **closing keyword는 PR이 repo의 default branch를 타겟할 때만 동작**하며, non-default branch(예: `develop`)를 타겟하면 무시돼 링크·auto-close가 전혀 안 생긴다. 이 하네스는 `config.git.baseBranch`와 실제 default branch가 다를 수 있어 E5-S3의 핵심 의사결정 지점이 된다.

## 1. sub-issue 계층 API (E5-S2)

### GA 타임라인
- Public beta 2024-09-30 → preview 2025-01-12 → **GA 2025-04-08/09** ([Evolving GitHub Issues and Projects](https://github.blog/changelog/2025-04-09-evolving-github-issues-and-projects/); [Introducing sub-issues](https://github.blog/engineering/architecture-optimization/introducing-sub-issues-enhancing-issue-management-on-github/)). GHES 3.18(2025-11)에도 포함.

### gh CLI 네이티브 지원 — v2.94.0 (2026-06-10)
`gh`가 sub-issue를 네이티브 지원한다 — raw API 불필요 ([Manage sub-issues from GitHub CLI](https://github.blog/changelog/2026-06-10-manage-sub-issues-types-and-dependencies-from-github-cli/); [cli/cli#13057](https://github.com/cli/cli/pull/13057/files)):
- 자식으로 생성: `gh issue create --parent <PARENT>` (번호/URL)
- 기존 자식 연결: `gh issue edit <PARENT> --add-sub-issue 123,124` / `--remove-sub-issue`
- 부모 설정: `gh issue edit <CHILD> --set-parent <PARENT>` / `--remove-parent`
- 계층 조회: `gh issue view`/`gh issue list --json parent,subIssues,subIssuesSummary`

### v2.94.0 미만 fallback — REST/GraphQL
**REST** ([docs.github.com REST sub-issues](https://docs.github.com/en/rest/issues/sub-issues?apiVersion=2022-11-28)):

| 연산 | Method + path |
|------|---------------|
| List | `GET /repos/{o}/{r}/issues/{n}/sub_issues` |
| Add | `POST /repos/{o}/{r}/issues/{n}/sub_issues` |
| Remove | `DELETE /repos/{o}/{r}/issues/{n}/sub_issue` (단수형!) |
| Get parent | `GET /repos/{o}/{r}/issues/{n}/parent` |

**핵심 함정**: `sub_issue_id`는 자식 이슈의 **internal database `id`**(정수)다 — issue number도, GraphQL node ID도 아니다. cross-repo(같은 owner 내) 가능성 때문에 number로는 모호하다. 번호를 넣으면 **500/404** ([cli/cli#10378](https://github.com/cli/cli/issues/10378), [#12258](https://github.com/cli/cli/issues/12258)). `gh api`로 `-f sub_issue_id=N`을 쓰면 문자열 강제변환으로 **422** → `--input -`로 정수 JSON 전달 필수.

```bash
# 1. database id 획득 (node_id 아님 주의)
ISSUE_ID=$(gh api repos/{o}/{r}/issues/{child_n} --jq '.id')
# 2. 링크 — --input으로 정수 전달 (-f는 422)
echo "{\"sub_issue_id\": $ISSUE_ID}" | gh api repos/{o}/{r}/issues/{parent_n}/sub_issues -X POST --input -
```

**GraphQL** — REST보다 신뢰도 높다고 보고됨 ([cli/cli#12258](https://github.com/cli/cli/issues/12258)). `addSubIssue(input:{issueId, subIssueId})`는 둘 다 **node ID** (또는 `subIssueUrl`). `createIssue`에 `parentIssueId`로 생성+링크 원샷도 가능 ([GraphQL Issues ref](https://docs.github.com/en/enterprise-cloud@latest/graphql/reference/issues)):
```bash
gh api graphql -f query='mutation($p:ID!,$c:ID!){addSubIssue(input:{issueId:$p,subIssueId:$c}){subIssue{number}}}' \
  -f p="$PARENT_NODE_ID" -f c="$CHILD_NODE_ID"
```

**ID 획득 주의** ⚠️: `gh issue view --json id`는 numeric database id가 아니라 **node_id를 반환**한다([cli/cli#10378](https://github.com/cli/cli/issues/10378)). 정수 id는 `gh api repos/{o}/{r}/issues/{n} --jq '.id'`, node ID는 `--jq '.node_id'`로 획득.

### 계층 제약
parent당 최대 **100 sub-issue**, **8단계 depth**, 같은 owner 내 cross-repo 가능 ⚠️(수치는 단일 third-party 소스 [awesome-copilot sub-issues.md](https://github.com/github/awesome-copilot/blob/main/skills/github-issues/references/sub-issues.md), 공식 재확인 권장).

## 2. PR-issue 링크 (E5-S3)

### 유일한 프로그램적 방법 = closing keyword
PR 본문에 closing keyword + 이슈 참조를 넣고 PR이 **default branch로 머지**되면 이슈가 auto-close된다 ([Linking a PR to an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). 키워드(대소문자 무관): `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved` ([Using keywords](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/using-keywords-in-issues-and-pull-requests)).

| 링크 대상 | 구문 | 예 |
|-----------|------|-----|
| 같은 repo | `KEYWORD #N` | `Closes #10` |
| 다른 repo | `KEYWORD OWNER/REPO#N` | `Fixes org/repo#100` |
| 여러 개 | 이슈마다 전체 구문 | `Resolves #10, resolves #123` |

**명시적 링크 API는 없다** — sidebar "Development" 메뉴의 수동 링크는 REST·GraphQL 어느 쪽으로도 프로그램 생성 불가. gh 메인테이너가 플랫폼팀 답변으로 확인: "no official GitHub API endpoint... no plan for supporting this" ([cli/cli#11405](https://github.com/cli/cli/issues/11405)) ⚠️(단일 소스이나 권위 있음). `closingIssuesReferences` GraphQL 필드는 **read-only**(조회만, 생성 불가).

### ⚠️ 결정적 제약 — default branch 요구
> "closing keyword는 PR이 repository의 **default** branch를 타겟할 때만 해석된다. 다른 branch를 타겟하면 키워드는 무시되고, 링크가 생성되지 않으며, 머지해도 이슈에 영향이 없다." ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue))

**이 하네스에 직접 영향**: `git-workflow.md`는 `config.git.baseBranch=main`이지만 `develop`을 integration branch로 쓰고 현재 브랜치도 `develop`이다. story PR이 **default branch가 아닌 branch를 타겟하면 `Closes #N`이 조용히 무시**돼 링크·auto-close가 안 생긴다. → E5-S3는 base branch가 실제 default branch인지 확인하는 게이트가 필수. (commit message의 키워드는 default branch 머지 시 이슈를 닫지만 PR이 "linked PR"로 표시되진 않음 — PR **본문** 키워드만 가시적 링크 생성.)

### cross-repo: reference는 되나 auto-close 안 됨
`Fixes owner/repo#N`은 cross-reference는 만들지만 머지 시 auto-close는 안 한다 ⚠️(커뮤니티 분석 [devactivity](https://devactivity.com/insights/streamlining-cross-repo-workflows-auto-closing-github-issues-with-external-prs/), 공식 문서는 구문 차이만 명시). 같은 repo story-issue→PR 흐름(하네스 표준)은 정상 auto-close.

### gh CLI 실무 패턴
`gh pr create`에 링크 전용 플래그 없음 — 본문에 키워드 삽입 ([gh pr create manual](https://cli.github.com/manual/gh_pr_create)). security.md shell-injection 규칙대로 `--body-file`/HEREDOC stdin 사용:
```bash
gh pr create --title "..." --body-file - <<'PR_BODY'
Implements the signup flow.

Closes #42
PR_BODY
```
`gh pr edit <n> --body-file`로 키워드 추가/제거(unlink는 키워드 삭제가 유일).

**검증 단계** — `closingIssuesReferences` JSON 필드는 gh ~v2.69+(PR [#10544](https://github.com/cli/cli/pull/10544), 2025-04-29)부터:
```bash
gh pr view <n> --json closingIssuesReferences --jq '.closingIssuesReferences[].number'
```
생성 후 이 조회로 story 번호가 있는지 assert → 키워드 파싱·링크 형성 확인(non-default-branch 실패도 빈 배열로 잡힘).

**권한/rate limit**: 로컬은 `repo` scope로 충분. GitHub Actions에서는 `closingIssuesReferences`가 `issues: read` permission 없이는 빈 배열 반환 ([cli/cli#11841](https://github.com/cli/cli/issues/11841)). GraphQL 5000pt/hr, REST 5000req/hr — per-PR 1회 조회는 무시할 수준.

### sub-issue ≠ PR-closing-link (혼동 금지)
sub-issue는 이슈↔이슈 부모-자식 계층(작업 분해), PR closing keyword는 PR↔이슈 링크(작업 완료→auto-close). E5-S2와 E5-S3는 **다른 메커니즘**이다 ([Browsing sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/browsing-sub-issues)).

## Key Takeaways (E5-S2-S3 스펙 직결)

- **gh 버전 게이트가 E5-S2 핵심 의사결정**: v2.94.0+ 네이티브(`--add-sub-issue`, 번호 입력, ID 저글링 불필요) vs 미만 fallback(GraphQL node ID 권장, REST는 database id 함정). adapter-github-issue가 두 경로 중 무엇을 지원할지 결정 + 버전 감지 게이트.
- **REST `sub_issue_id` = database id 함정**: 반드시 `gh api ... --jq '.id'`로 획득, `--input -`로 정수 전달. `gh issue view --json id`는 node_id라 오용 주의.
- **E5-S3 default-branch 제약이 최대 리스크**: `Closes #N`은 PR base = repo default branch일 때만 동작. 하네스 develop/main 이원 구조에서 base 확인 게이트 없으면 링크가 조용히 실패. → 핵심 Open Question.
- **명시적 링크 API 부재**: PR-issue 링크는 본문 closing keyword가 유일. `--add-issue` 시도 금지(API 없어 blocked).
- **검증 = `closingIssuesReferences` 조회**: 생성 후 story 번호 assert로 링크 성립 확인(non-default-branch 실패 감지 겸용).
- **E5-S2/S3 배선 경계**: adapter-github-issue에 연산 추가(E5-S2 sub-issue link, E5-S3 PR-link)까지가 본 토픽. flow-spec/flow-pr 배선은 E3-S2/E3-S5 소관(github-issue-anchor.md와 정합).
