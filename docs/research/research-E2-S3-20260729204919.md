## Executive Summary

도구 설정을 계층화한 선례는 거의 예외 없이 **"레포에 커밋되는 공유 층 + 커밋되지 않는 개인/머신 로컬 층 + 상위 관리 층"** 3~6단 스택으로 수렴하며, 우선순위는 좁은 스코프가 넓은 스코프를 이긴다 ([Claude Code settings](https://code.claude.com/docs/en/settings), [Devin CLI](https://docs.devin.ai/cli/reference/configuration/global-vs-local), [repo_man](https://docs.omniverse.nvidia.com/kit/docs/repo_man/latest/docs/configuration.html)). 다만 **모든 키가 같은 방식으로 병합되지는 않는다** — Claude Code는 일반 설정은 override, 권한 규칙은 스코프 간 merge로 다르게 처리하고, repo_man은 leaf 값만 덮어쓰고 dict(table)은 병합하지 않는다고 명시한다. 병합 규칙은 키 종류별로 계약에 적어야 하는 항목이지 구현 세부가 아니다.

설정(config)과 런타임 상태(state)·캐시(cache)의 분리는 XDG Base Directory Specification이 `$XDG_CONFIG_HOME` / `$XDG_STATE_HOME` / `$XDG_CACHE_HOME` / `$XDG_DATA_HOME`를 각각 별도 베이스 디렉토리로 규정하며 표준화돼 있다 ([freedesktop.org, v0.8](https://specifications.freedesktop.org/basedir/latest/)). 이 분리를 지키지 않아 실제로 깨진 사례가 둘 관측된다: omegon은 tracked `state.json`이 타임스탬프 churn으로 릴리스 커밋을 오염시켜 "tracked baseline + ignored runtime state" 분리 설계로 전환 중이고 ([omegon lifecycle-state-runtime-split](https://github.com/styrene-lab/omegon/blob/main/docs/design/lifecycle-state-runtime-split.md)), cadence는 tracked `state.json`의 `activePhase` 포인터가 **worktree마다 다른 값을 가져 브랜치 병합 시 확정적 충돌**을 일으켜 JSON이 깨지는 버그를 안고 있다 ([cadence #177](https://github.com/manehorizons/cadence/issues/177)). 후자는 tack의 허브↔worktree dev-context 문제와 같은 구조다.

스키마 측면에서는 설정 파일에 **명시적 포맷 버전 필드**를 두고 semver 정책을 문서화하는 것이 확립된 관행이다 — OpenTelemetry는 `file_format` 속성과 "stable MAJOR 내에서 MINOR/PATCH 업그레이드 시 기존 설정이 무효화되지 않음"을 계약으로 못 박는다 ([OTel VERSIONING.md](https://github.com/open-telemetry/opentelemetry-configuration/blob/main/VERSIONING.md)). 변경 안전성 등급은 "선택 필드 추가=안전 / 삭제·이름변경·타입변경=파괴적"으로 정리된다 ([Jsonic](https://jsonic.io/guides/json-schema-migration), [Confluent Schema Evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)).

## 1. 계층화와 우선순위 — 무엇이 몇 층이고 누가 이기나

**Claude Code**는 4개 스코프를 정의한다 — Managed(조직 배포), User(`~/.claude/`), Project(`.claude/`, 커밋됨), Local(`.claude/settings.local.json`, gitignore). 적용 우선순위는 Managed > CLI 인자 > Local > Project > User이며, 낮은 층은 상위 층이 그 키를 지정하지 않을 때만 적용된다 ([Claude Code settings](https://code.claude.com/docs/en/settings)).

주목할 두 가지:
- **권한 규칙은 override가 아니라 merge**다. 같은 파일 안에서도 키 종류에 따라 병합 의미가 갈린다.
- `settings.local.json`은 **worktree를 통해 main checkout으로 해석**돼, 어느 worktree/하위 디렉토리에서 세션을 시작하든 한 파일이 적용된다. 즉 "worktree마다 다른 로컬 설정"을 의도적으로 배제한 설계다.

**Devin CLI**는 5층을 명시 표로 제공한다 — Organization/Team(오버라이드 불가) > Session(메모리 전용) > Project Local(`.devin/config.local.json`, gitignored) > Project(`.devin/config.json`, 팀 공유) > User(`~/.config/devin/config.json`) ([Devin CLI](https://docs.devin.ai/cli/reference/configuration/global-vs-local)). 각 층에 "무엇을 넣어야 하는가"를 용도별로 문서화한 점이 참고할 만하다(개인 모델 선호·테마는 User, 팀 표준은 Project).

**repo_man**은 6개 config가 순차 병합되며, 뒤에 오는 것이 앞을 덮는다. 핵심 진술: **"병합(오버라이드)은 leaf 값(정수·문자열·배열) 단위로 일어나고 dict(table) 단위로는 일어나지 않는다"** ([repo_man](https://docs.omniverse.nvidia.com/kit/docs/repo_man/latest/docs/configuration.html)). 배열이 leaf로 취급된다는 점(= 병합이 아니라 통째 교체)은 tack의 `config.graphify.targets` 같은 배열 키에 그대로 걸리는 결정 사항이다.

**Supabase CLI**는 개념 분리를 타입으로 못 박았다 — `ProjectConfig`(디스크의 지속 설정), `ProjectEnvironment`(병합된 env 맵), `ProjectContext`(런타임 번들), 그리고 이들과 **별개인** `CliConfig`(액세스 토큰·캐시 루트·디버그/텔레메트리 플래그 등 CLI 런타임 설정) ([Supabase CLI](https://github.com/supabase/cli/blob/develop/packages/config/docs/project-config-loading.md)). 탐색은 cwd에서 위로 올라가 **가장 가까운** `supabase/` 한 곳만 쓰고 상위 조상들과 병합하지 않는다 — "nearest wins, no ancestor merge"는 모노레포·worktree에서 예측 가능성을 지키는 규칙이다.

## 2. config vs state vs cache — 분리 기준과 실패 사례

**XDG Base Directory Specification (v0.8, 2021-05-08)**은 사용자별 파일을 용도별 베이스 디렉토리로 분리한다 — data(`$XDG_DATA_HOME`), config(`$XDG_CONFIG_HOME`), **state(`$XDG_STATE_HOME`)**, cache(`$XDG_CACHE_HOME`), 그리고 탐색 경로 집합(`$XDG_DATA_DIRS`, `$XDG_CONFIG_DIRS`) ([freedesktop.org](https://specifications.freedesktop.org/basedir/latest/)). state는 2021년에 추가된 비교적 최근 축으로, "재시작 사이에 유지되지만 config도 data도 아닌 것"(로그·히스토리·최근 상태)을 담는 자리다.

**실패 사례 A — 릴리스 오염 (omegon)**: `ai/lifecycle/state.json`이 tracked라 런타임 쓰기가 매 `git status`에 뜨고 릴리스 패치 커밋을 오염시키며, 다른 브랜치/세션 상태가 안정 릴리스 라인에 새어 들어갔다. 진단은 "한 파일이 **프로젝트 산출물**과 **런타임 상태 DB** 두 역할을 동시에 지려 했다"이고, 채택 방향은 tracked baseline(`baseline.json`) + ignored runtime state(`.omegon/lifecycle/state.json` + `.lock`) 분리다. 마이그레이션 정책까지 설계에 포함했다 — 새 경로가 없고 레거시가 있으면 1회 복사, 런타임은 레거시를 절대 갱신하지 않고 명시적 export 명령으로만 baseline을 쓴다 ([omegon](https://github.com/styrene-lab/omegon/blob/main/docs/design/lifecycle-state-runtime-split.md)).

**실패 사례 B — worktree 간 확정적 충돌 (cadence #177, 2026-07-12, open)**: `.cadence/state.json`의 `activePhase`·`activeDraft`·`loopPosition` 같은 값은 본질적으로 **worktree별 일시적 루프 위치**인데 tracked 파일에 들어 있다. 서로 다른 phase를 진행하는 두 worktree가 같은 키에 서로 배타적인 값을 쓰므로, 병합 시 `<<<<<<< HEAD` 마커가 JSON을 깨뜨리고 후속 명령이 파싱 에러로 죽는다. 제안된 해소책 3안(선호 순):
1. `.git/<tool>/`처럼 **tracked tree 바깥**에 쓴다 — git의 `.git/worktrees/<name>/` 메커니즘 덕에 자연히 worktree-local이고 커밋 그래프에 아예 진입하지 않는다.
2. 레포 루트 아래 두어야 한다면 기본 `.gitignore` 항목을 함께 배포한다.
3. "어느 worktree가 무엇을 하는지"의 교차 가시성이 정말 필요하면, 단일 mutable 포인터가 아니라 **worktree/브랜치로 키가 나뉜 additively-mergeable 원장**으로 별도 설계한다 ([cadence #177](https://github.com/manehorizons/cadence/issues/177)).

세 번째 항목은 "공유 상태가 필요하다"와 "파일을 tracked로 둔다"가 같은 말이 아님을 분명히 한다 — 공유가 필요하면 병합 가능한 자료구조를 설계하라는 뜻이다.

## 3. 스키마 정의·네임스페이스·버전닝

**포맷 버전 필드**: OpenTelemetry declarative configuration은 `file_format` 속성을 두고 semver 정책을 문서화한다. 목표 진술이 명확하다 — "특정 stable MAJOR 버전에 맞춘 설정을 제공한 사용자는 MINOR·PATCH 업그레이드에서 설정이 무효화되거나 해석이 바뀌지 않으리라 기대할 수 있어야 한다" ([OTel VERSIONING.md](https://github.com/open-telemetry/opentelemetry-configuration/blob/main/VERSIONING.md)). 스키마 버전이 구현 기대와 어긋날 때의 동작(file format 불일치 처리)까지 별도 절로 규정한다.

**변경 안전성 등급**: 선택 필드 추가(기본값 포함)는 backward-compatible, 필드 삭제·이름 변경·타입 변경은 파괴적이라는 구분이 공통이다. 문서 자체에 숫자형 `schemaVersion`을 심고 v1→vN 변환 함수를 두는 패턴, additive 변경은 변환 함수 0개로 처리하는 패턴이 정리돼 있다 ([Jsonic - JSON Schema Migration](https://jsonic.io/guides/json-schema-migration), [Jsonic - Migration Strategy](https://jsonic.io/guides/json-migrations)). 메시징 계열의 Schema Registry는 같은 판정을 BACKWARD/FORWARD/FULL 호환 모드로 형식화한다 ([Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html), [Solace best practices](https://docs.solace.com/Schema-Registry/schema-registry-best-practices.htm)).

**스키마를 계약으로 취급**: "JSON Schema가 계약이고 언어별 타입은 그 투영(projection)"이라는 원칙 진술이 있다 ([Beach 문서](https://cool-ai.org/docs/configuration-schemas)). 여러 소비자(여기서는 Claude·Codex)가 같은 설정을 읽는 구조에서는 스키마 파일이 SSOT이고 각 도구의 파서는 파생물이라는 배치가 정합적이다.

**시작 시 fail-fast 검증**: 설정 오류를 런타임 지연 실패가 아니라 시작 시점 예외로 끌어올리는 것이 일반 권고다. .NET 진영의 eager validation 논의, strict mode(알 수 없는 필드·타입 불일치·필수 필드 누락 → 즉시 실패) 사례가 대표적이다 ([dotnet/runtime #36391](https://github.com/dotnet/runtime/issues/36391), [Serverless API Gateway strict mode](https://docs.serverlessapigateway.com/reference/config-schema-overview/config-strict-mode)). 네임스페이스별 스키마 등록(namespace + 스키마 객체) 후 등록 시점에 검증 실패를 던지는 ConfigStore 패턴도 관측된다 ([neststack](https://github.com/mikecoj/neststack)).

## Key Takeaways

- **3층 분리(정적 커밋 config / 공유 런타임 상태 / 로컬 휘발 캐시)는 XDG가 이미 표준화한 축과 일치한다.** 스펙에서 각 층의 정의를 XDG 용어(config·state·cache·data)에 맞춰 진술하면 경계 판정이 논쟁 대상에서 참조 대상이 된다.
- **병합 의미를 키 종류별로 계약에 명시해야 한다.** override(스칼라)·merge(권한 같은 집합형)·통째 교체(배열)는 서로 다른 규칙이고, 실제 도구들은 이 셋을 혼용한다. `config.graphify.targets` 같은 배열 키가 첫 시험 사례다.
- **worktree 경계는 config 설계의 1급 제약이다.** cadence #177은 tracked 단일 mutable 포인터가 다중 worktree에서 확정적으로 깨진다는 실증이고, Claude Code는 반대로 로컬 설정을 main checkout으로 해석해 이 문제를 회피한다. tack은 이미 worktree 격리를 쓰므로 어느 쪽을 택할지 스펙에서 결정해야 한다.
- **"공유가 필요하다"는 "tracked로 둔다"와 다르다.** 교차 가시성이 필요하면 worktree/브랜치로 키가 나뉜 additively-mergeable 원장을 설계하라는 것이 cadence의 결론이며, 이는 E4 Mongo 공유 레지스트리 방향과 정합한다.
- **설정 파일에 포맷 버전 필드를 넣고 변경 등급을 문서화한다.** OTel의 `file_format` + semver 정책이 최소 모델이다. 선택 필드 추가는 안전, 삭제·이름변경·타입변경은 파괴적으로 분류하고 마이그레이션 경로를 함께 규정한다.
- **스키마는 계약, 파서는 투영.** Claude·Codex 두 소비자가 같은 설정을 읽는 구조에서는 스키마 파일이 SSOT여야 하며, 시작 시 fail-fast 검증(알 수 없는 키·타입 불일치·필수 누락)을 기본으로 둔다.
- **마이그레이션 정책을 설계에 포함한다.** omegon의 규칙이 실용적 모델이다 — 새 경로 부재 + 레거시 존재 시 1회 복사, 런타임은 레거시를 절대 쓰지 않음, 레거시로의 반영은 명시적 export 명령으로만.

## Methodology

7개 쿼리를 실행했다. 사용 어댑터: adapter-exa(5 쿼리), adapter-firecrawl(2 쿼리 + 1 스크레이프). 실패한 어댑터: 없음. 조사한 서브 질문: (1) 도구 설정의 계층화·우선순위 병합 선례, (2) config vs state vs cache 분리 기준과 실패 사례, (3) 스키마 정의·네임스페이스·버전닝 관례. 검색 결과에서 중복 제거 후 8개 URL을 심층 판독(exa `/contents`)했고, XDG 사양은 firecrawl `/v1/scrape`로 본문을 확인했다. 분석한 소스: 14.

**한계**: (a) 하네스/에이전트 도구의 worktree-config 상호작용을 다룬 1차 자료가 적어 근거가 cadence·omegon 두 사례에 집중돼 있다 — 둘 다 단일 출처 관측이므로 교차 검증되지 않았다. (b) 위험 tier 필드처럼 "설정 값으로 워크플로우 동작을 분기시키는" 구체 선례는 검색으로 확보하지 못했다(insufficient data found) — 이 부분은 내부 승계 소스와 D7 결정에 의존해야 한다.
